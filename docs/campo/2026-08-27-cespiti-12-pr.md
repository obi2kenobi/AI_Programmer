## 2. Metodo (contributo a `METHOD.md`)

- **Un batch = un tema coerente = una PR indipendente.** Ogni batch parte da un branch fresco su `main`, non impilato sugli altri, salvo una dipendenza dichiarata esplicitamente nel piano (Batch 8 → Batch 7): questo mantiene ogni PR mergeabile e revisionabile da sola, al costo di doverne risolvere i conflitti testuali al momento dell'integrazione in sequenza.
- **"Esegui, non leggere" anche sulle funzioni che toccano Sheet/Drive/PropertiesService.** Le funzioni pure vanno in `Tests.gs` e girano nell'harness Node standard; per quelle impure (creano uno spreadsheet, leggono/scrivono Script Properties) è stato scritto uno script di verifica dedicato con stub minimi delle API GAS in memoria, eseguito per davvero prima di aprire la PR — mai fidarsi della sola lettura del codice per la parte che tocca API esterne.
- **Gotcha del sandbox Node (`vm` module):** quando il codice GAS dichiara un binding globale con `let X = null;` (es. `REPORT_SS` in `Config.gs`), non è possibile sovrascriverlo da fuori assegnando `ctx.X = valore` prima di eseguire il sorgente nel context — `let`/`const` di primo livello non diventano proprietà dell'oggetto contesto passato a `vm.createContext`. La sequenza corretta è: eseguire il sorgente con `vm.runInContext(src, ctx)`, poi fare una seconda chiamata `vm.runInContext('X = valoreStub;', ctx)` con una semplice assegnazione (non una nuova dichiarazione) — questa risolve alla lexical binding già creata dal sorgente. Impattato più volte in questa sessione (`REPORT_SS`, `REPORT_CONFIG.dataAl`).

## 3. Proposte per il catalogo pattern (`AI_Programmer/patterns/`)

Candidati emersi da questa sessione — non ancora aggiunti al catalogo (nessun accesso al repo `AI_Programmer` da questa sessione), proposti con l'evidenza concreta trovata nel codice.

### Pattern candidato: `riga-in-coda-non-interposta`

**Descrizione:** quando si aggiunge una sezione a un foglio/report con posizioni di riga già hardcoded altrove (es. `sheet.getRange(8, 1).setFontWeight('bold')` per un titolo di sezione), la nuova sezione va **sempre aggiunta in coda**, mai interposta tra sezioni esistenti — anche se logicamente apparterrebbe altrove. Interporla sposta silenziosamente ogni riferimento di riga hardcoded successivo.

**Evidenza:**
- `Main.gs`, `generateCopertina_()` (PR #25, Batch 3): la sezione "DATI GREZZI BUSINESS CENTRAL" è stata aggiunta dopo il loop "FOGLI GENERATI" invece che dentro "RIEPILOGO" (dove apparterrebbe logicamente), proprio per non spostare le righe bold hardcoded a 8 e 15. Nella PR #31 (Batch 9) la riga "Versione" usa lo stesso principio con un calcolo di riga dinamico (`15 + REPORT_SHEETS.length + 2`) invece di un altro numero fisso, restando corretta anche se in futuro cambia il numero di fogli generati.
- **Errore auto-corretto durante la sessione stessa** (PR #25, Batch 3): un primo tentativo aveva inserito la sezione dentro "RIEPILOGO", scoperto e corretto prima del commit grazie alla verifica con stub dedicata (§2) che ha mostrato la riga "FOGLI GENERATI" spostata dalla riga 15 attesa.

**Dove:** `patterns/` — pattern di scrittura codice, non solo di revisione.

### Pattern candidato: `dipendenza-tra-rami-paralleli`

**Descrizione:** quando più PR indipendenti partono dallo stesso `main` (senza dipendenze dichiarate), nessuna può richiamare una funzione/parametro introdotto da un'altra PR non ancora mergiata — anche se logicamente "verrebbe naturale" farlo. Il branch, preso da solo, deve restare eseguibile: la funzione semplicemente non esiste ancora sul suo `main` di partenza.

**Evidenza — due occorrenze auto-corrette nella stessa sessione:**
- PR #25 (Batch 3): `writeCategoryTable_` chiamava inizialmente `writeEmptyMessage_()` — funzione introdotta dalla PR #24 (Batch 2), non presente sul branch di Batch 3 (partito da `main` prima del merge di #24). Corretto sostituendo con un commento esplicito prima del commit.
- PR #28 (Batch 6): `generateEsclusi()` passava inizialmente un 4° parametro `emptyMessage` a `writeSheetData()` — firma introdotta anch'essa dalla PR #24, non presente sul branch di Batch 6. Corretto rimuovendo il parametro prima del commit.

**Dove:** `patterns/` — specifico per un workflow a PR parallele indipendenti (rilevante quando più agenti/sessioni lavorano sullo stesso repo in batch separati).

### Nota di igiene test: soglia non raggiungibile dopo arrotondamento

Non un pattern di bug, ma una decisione di test degna di nota: durante il Batch 12 è stato valutato se aggiungere un test sul confine esatto `THRESHOLDS.DELTA_ZERO` (0.005) nel filtro di `buildDashboardModel_`. Scartato perché il valore confrontato è già passato per `round2()` (arrotondamento a 2 decimali) prima del confronto — il valore intermedio 0.005 non è mai raggiungibile come input reale del filtro (arrotonda sempre a 0.00 o 0.01+). Un test costruito su quel confine sarebbe stato tecnicamente eseguibile ma privo di significato, perché non rispecchierebbe alcun percorso dati reale. Utile come promemoria generale: **verificare che un caso limite sia raggiungibile attraverso la pipeline reale prima di scrivere un test per quel confine**, non solo che la funzione isolata lo accetti come input.

**Dove:** `METHOD.md` o una nota nella checklist di test-review.
